An agent working in a project with an sdd graph works from what the graph records, read in full and together with what changed it, never from what it believes the graph holds.

Left to itself, an agent answers a question about a past decision from the one entry it happened to open, or from its memory of the graph. It drafts a decision an older entry already settled, reads an entry without the later one that renamed everything in it, and writes entries that break the project's own rules for the graph. sdd's way of thinking (20260810-190000-s-prc-way) asks the opposite: the graph prepares the dialogue, and contributing without having looked means making things up. An instruction alone does not hold an agent to that: a skill telling it to search first is read, then skipped under the pressure of the task at hand. sdd-helpers, a Claude Code plugin installed once per machine whose hooks hold an agent's questions, drafts and graph writes to reads of the graph, exists to close that distance in every session on the machine, without anyone running anything by hand.

The pull pushes against answering from belief, taking an entry's summary as fact, reading an entry without its downstream chain, and captures that bypass the project's rules for the graph.

The working test for any change to sdd-helpers: does it make it harder for an agent to ask, draft or capture without having read what the graph holds on the matter, while keeping the reading itself no costlier than it needs to be?

The pull strains against the time and tokens of the agent and of the person working with it. Every read owed costs both, and a gate that refuses too much teaches people to switch it off, which loses the pull entirely; the same way of thinking treats such friction as a signal, not as a cost to push through. The pull is therefore toward the reads that matter for the call at hand, with reads already done counted and output the agent was already shown kept short, never toward the most reads.
